# Tuya / Smart Life

## Tuya / Smart Life

Smart Life devices are Tuya devices. This project uses `tinytuya` as a local LAN control foundation. Runtime reads and commands use the local keys stored in gitignored `devices.json`; they do not require an active Tuya Cloud project once that file exists.

**Adding a plug later needs no terminal** — pair it in the Smart Life app, then tap **Add** on the Devices tab (see below). The bootstrap here is only for the *very first* `devices.json` on a new machine.

One-time Tuya bootstrap, only needed when `devices.json` must be generated from scratch:

1. Register or log in at `https://iot.tuya.com/`.
2. Create a **Smart Home** Cloud Project in the **Central Europe** data center.
3. Link the Smart Life mobile app account to that project by scanning the QR code from the Tuya developer portal.
4. Copy the project's **Access ID / Client ID** and **Access Secret / Client Secret** into `.env` for the wizard:

| Key | Meaning |
|-----|---------|
| `TUYA_API_KEY` | Tuya Cloud Project Access ID / Client ID, used only for TinyTuya bootstrap. |
| `TUYA_API_SECRET` | Tuya Cloud Project Access Secret / Client Secret, used only for TinyTuya bootstrap. |
| `TUYA_REGION` | Tuya data-center region for bootstrap. Use `eu` for Central Europe. |

Then fetch the device list and local keys:

```powershell
& .\.venv\Scripts\python.exe -m tinytuya wizard
```

The wizard writes `devices.json` in the project root. That file contains device IDs, local keys, IPs, protocol versions, and DPS mappings; it is required for LAN-mode control and is gitignored because it contains secrets. TinyTuya may also write `tinytuya.json`; that is gitignored as well. Energy DPS varies by plug model, so `src/tuya_client.py` reads the captured `mapping` block instead of assuming fixed DPS indexes.

Once that file exists, the three `.env` keys above stay in use for the in-app **Add** action only — `src/tuya_cloud.py` passes them to `tinytuya.Cloud` directly, so no wizard run and no QR scan is ever needed again. The QR scan in step 3 is a *one-time account link*, not a per-device step: every device paired in Smart Life afterwards is already visible to the cloud project. If **Add** reports no new devices, the plug is paired to a different Smart Life account than the one linked in step 3.

### 🔌 Devices tab

The PWA's **Devices** tab is the single surface for every local device It opens with the **Power** glance card — what is on and drawing power: the live plug total, the three biggest draws by name, and the **UPS** as a row whose sheet holds the PC-fleet shutdown. Below it, **Lights**, **Blinds**, **Plugs** and **Circuits** are open groups on the shared row (a leading glyph, the name, one muted line, one trailing item), then **Home Assistant** and **Network**. A **plug row** is **name · watts while on (else Off) · switch** (**live wattage on metered plugs**, so solar/load decisions are obvious without opening the vendor app); a **light row** is **name · brightness and warmth · switch**, with the sliders in the light sheet (see *Elgato lights* below); a **blind row** is **name** and one segmented **Up · Stop · Down** verb (each segment a real 44 px target named in words for screen readers) wired to the cover open/stop/close path. It is **cloud-free at runtime** — it reads `devices.json`, `/api/lights`, and local LAN status only.

Lights sit in this tab rather than on a top-level tab of their own: they are local device controls like the plugs and blinds, and a seventh peer tab would be more navigation weight than a phone PWA should carry.

The Power card's **UPS** row shows the local UPS (on mains or on battery · charge% · runtime, an exception chip when it needs you), and its sheet the full reading; Home keeps its one-line tile. `GET /api/ups` reads the USB-connected APC Smart-UPS through NUT when the local `upsc` server is available, falls back to a one-shot NUT USB-HID probe, then falls back to Windows battery telemetry. The current APC SMT1000IC USB-HID path reliably exposes status, charge, runtime, battery voltage, model, manufacturer, and serial; it does **not** expose `ups.load`, `input.voltage`, or `output.voltage` through NUT on this machine.

**Power notifications (Telegram).** **Settings › Notifications › UPS power**
has two toggles — **Mains power lost** and **Power restored** — both default **on**; they push a Telegram message when the UPS crosses between mains and battery. Persisted to gitignored `config/power_notify_prefs.json` (`…sample.json` committed) via `GET`/`PUT /api/ups/notify-prefs`. Because the browser tile only polls while the Devices tab is open, reliable alerts need a server-side watcher: a background **power monitor** (`app/webapp/power_monitor.py`, started in the webapp lifespan) reads the UPS every `POWER_MONITOR_POLL_INTERVAL_S` (default 60 s) in a worker thread and fires edge-triggered on the `mains_online` transition. Set `POWER_MONITOR_ENABLED=0` to disable it. Uses the same `src/notify/` Telegram credentials as the alarm alerts; transitions are recorded to gitignored `logs/power.jsonl` via the shared activity log.

**PC-fleet shutdown on low UPS runtime.** The **UPS sheet** (Devices › Power › UPS) holds the fleet shutdown: a master switch ("Shut down fleet on low UPS runtime", default on), a configurable trigger threshold (runtime-remaining ≤ X minutes, default 15, clamped 1–240), and a live machine roster pulled from the local-llm-hub's machine API (`GET /api/pc-fleet/machines` proxies the hub's `GET /admin/api/machines/status` on loopback `127.0.0.1:8000`, overridable via `PC_FLEET_HUB_BASE`) — a machine enrolled in the hub registry appears here automatically, with a per-machine include toggle and a **Wake** button (proxying the hub's Wake-on-LAN endpoint) on down machines. Prefs persist to gitignored `config/pc_fleet.json` (`…sample.json` committed; `enabled` seeds once from the legacy `auto_shutdown_low_battery` value on first load) via `GET`/`PUT /api/pc-fleet/prefs`.

**Shut down or hibernate the tower.** Under the threshold row the UPS sheet has a two-way **This PC, last** control: **Shut down** (default) or **Hibernate**, saved as `tower_action` in `config/pc_fleet.json` (an unknown value reads back as `shutdown`). Satellites always shut down through the hub; only the tower, which still goes last, honours the choice. **Hibernate, not sleep:** sleep keeps the session in RAM, so if the UPS then runs flat the work is lost exactly as in a crash, while hibernate writes it to disk, survives the power loss and resumes the session when power returns. Windows can schedule and cancel a shutdown (`shutdown /s /t 180`, undone by `shutdown /a`) but not a hibernate (`shutdown /h` takes no `/t`), so with Hibernate the same 180 s grace window is an in-process timer: when it elapses the app runs `shutdown /h`, and mains returning inside the window cancels the timer. The Telegram alert names the action and both outcomes are logged to `logs/power.jsonl` (`low_battery_hibernate`, `low_battery_shutdown_cancelled` with `hibernate_cancelled`). Two edges to know: a webapp restart inside the window drops the timer, but the next power-monitor tick re-fires the trigger (a safety trigger is never suppressed on first observation) and starts a fresh 180 s window; and if Windows refuses to hibernate (hibernation disabled) the app falls back to a 30 s shutdown rather than leave the tower to run flat. Check with `powercfg /a` that Hibernate is listed as available.

When the UPS is on battery and its reported runtime drops to the configured threshold, the orchestration — if the master switch is on — shuts down every **included, currently-up satellite** first via the hub's `POST /admin/api/machines/{id}/shutdown` (fire-and-forget SSH under the hood; one short best-effort confirmation re-poll, ≈ ≤9 s total), sends a Telegram alert listing each machine's outcome (`shutdown sent` / `confirmed down` / `excluded` / `already down, skipped` — a normal outcome for satellites on raw grid power / `failed: …`), then schedules the tower's own graceful Windows shutdown **last** via `src/host_shutdown.py` (`shutdown /s /t 180 /c "…"`, the 180-second grace window). The tower's shutdown is never blocked by satellite failures: hub unreachable → tower-only shutdown, and the Telegram message says so. Master off means **no automatic shutdowns at all** — satellites and tower stay up until the end. The trigger fires once per outage (edge-triggered in `power_monitor.py`'s process-memory state) and is **not** suppressed on the monitor's first observation — if the webapp restarts while the UPS is already critically low, it still triggers. If mains power returns before the tower's grace period ends, the pending tower shutdown is cancelled (`shutdown /a`) and the trigger resets — already-dispatched satellite shutdowns cannot be recalled. The shutdown call is hard-blocked under `pytest` (mirrors the Telegram notifier's pytest guard in `src/notify_config.py`) so the test suite can never trigger a real shutdown.

> **Blind position is up/stop/down only.** Every blind (Maxcio "Curtain switch", Tuya category `qt`) exposes a single open/stop/close DPS with **no native position % and no feedback** (confirmed by a live `tinytuya` DPS dump). Percentage **presets** would therefore need a time-based approximation (calibrated travel-time + a timed stop) and are not built.

- **Move every blind at once:** the Blinds group's **All blinds** row, its own Up · Stop · Down verb, sends one `POST /api/tuya/covers` naming every blind the group currently lists (a user-hidden blind stays out of it). `src/blind_automation.py` fans the per-blind commands out **in parallel**, one worker thread each, so the blinds start together instead of rippling across the house one LAN round trip at a time. One blind failing never stops the others: the response reports each blind's outcome and the toast names the ones that did not move, which are then retried (below). **Stop always goes out at once:** the card never holds a tap behind an earlier one still in flight, and only the latest tap's answer is toasted.
- **Schedule the blinds:** the Blinds group's **Schedule** row opens the schedule sheet, whose list holds daily up/down entries, each with a time, weekdays, **Up** or **Down**, which blinds it moves (none picked = every blind) and an **Only when** presence condition: *Always*, *Someone is home* or *Nobody is home*, judged from the webhook presence at the entry's fire time. That gives the household pattern of a 7:00 weekend up, a weekday up that differs when someone is home versus out, and one daily down. Same summary-row + staged edit dialog as the alarm schedules; persisted to gitignored `config/blind_schedules.json` (`config/blind_schedules.sample.json` committed) via `GET`/`PUT /api/blinds/schedules`. The tray-owned webapp fires due entries (`app/webapp/blind_schedules.py`) with the **AC schedule's timing**: a two-minute catch-up window after HH:MM, so a restart hours later never replays a stale morning "up", and at most once a day per entry. A presence miss (or no tracked people at all, presence unknown) skips the entry for that day rather than firing when someone later arrives. A blind that fails is retried in the background (see *Automatic moves retry a failed blind* below); only a move that could not even be attempted is retried on the next poll inside the window. Fired, skipped and failed runs land in the activity log. Disable with `BLIND_SCHEDULES_ENABLED=0`.
- **Blinds follow the automatic alarm:** the schedule sheet's **Follow the automatic alarm** switch (**off by default**, persisted to gitignored `config/blind_alarm.json` via `GET`/`PUT /api/blinds/alarm-pairing`). When everyone has left and the presence automation arms **full**, every blind gets close. With no position feedback, a blind that is already down just receives a harmless close. When the first person arrives and it disarms, every blind goes up **in daytime only**. The **kids-home** override (a perimeter arm) and a partial arm leave the blinds where they are. Daytime is the blinds schedule's own day for today: the earliest enabled **Up** to the latest enabled **Down**. When the schedule defines no such day, it is the sun being above the horizon at the home location (`config/location.json`). When neither is known, daytime is unknown and the blinds stay put. It runs inside the presence automation (`app/webapp/presence_automation.py`), only after the panel **confirmed** the arm/disarm and after that action is recorded, so a failed alarm command never moves a blind, and a blind failure never touches the alarm outcome, its record or its notification. No second presence detector.
- **A failed blind is retried.** When a scheduled, follow-the-alarm or manual (All up / All down, or one blind's verb) move reaches a blind that is offline, only the blinds that failed are re-sent after **30 s, 60 s, 120 s and 240 s** (about 7.5 minutes), each dropping out as soon as it moves; a failed **Stop** retries after 2, 4 and 8 s instead, within the blind's travel time. The retries run in the background, so they never delay the schedule tick, the alarm path or the card's answer. **A newer command wins:** every command a blind receives is numbered, and a pending retry is dropped once a newer one (another schedule, a manual tap, a Stop, another alarm move) has reached that blind, so an old "open" can never undo a newer "close" or "stop". Commands to one blind go out one at a time in tap order, each re-checking it is still the newest when its turn comes: a Stop tapped while an earlier move still waits on an unresponsive blind lands right after it, never before, and a stale command queued behind it is dropped. Success, on the first try or after retries, is an info log only. A blind still failing after the last retry sends **one Telegram message per move** through the alarm notifier, naming the blinds by display name, e.g. `🪟 Blinds could not open: <blind name> (schedule 08:00). Retried for ~7.5 min.` (`(manual)` for a tap). For automatic moves the activity-log record is written once the move has settled, with the final outcome and the attempt count; a manual tap answers with its first attempt at once and writes no record. A blind that does not answer is seen as failed: `set_cover` writes the mapped control DPS itself and checks the reply, because TinyTuya's `CoverDevice` helpers return nothing and would log every dropped command as sent. The value it writes is the blind's own: each blind's cover type is detected from its local `status()` with TinyTuya's `CoverDevice` value sets (string-numeric blinds take `'1'` open, `'2'` close, `'0'` stop, whatever the cloud schema lists), the value written is logged (`close -> '2'`), and a blind whose type can't be determined gets a distinct, logged error instead of a guess. The type is a property of the hardware, so it is persisted to a gitignored `config/tuya_cover_types.json` (`device_id` → type; a missing file is not an error) and is also learned from the passive poll's status read: a blind that reads `'3'` — in no value set — right after a restart is not stranded, because its type was learned while it still showed a known value. `'3'` itself stays unknown and is never guessed.
- **Tuya lights live in the Lights card:** a Tuya device in a lighting category (`dj`, `dd`, `dc`, `xdd`, `fwd`, `tgq`, `tgkg`) or whose switch is the lighting `switch_led` code carries `is_light: true` on its `GET /api/tuya` card, and the PWA lists it as a row in the **Lights** group beside the Elgato lights rather than under Plugs. It still toggles over the plug switch path, follows the Plugs card's Hidden / Reachable-only filters, and joins the Lights card's **All on / All off**. A smart plug feeding a lamp stays a plug. A **dimmer** (a `bright_value` / `bright_value_v2` DPS in its cloud mapping) also gets the Elgato row's **Brightness** slider: 1–100 % maps linearly onto the device's own raw range from that mapping (e.g. 25–255), only the brightness DPS is written (an off light stays off), and one request goes out per release, not per pixel.

- **Rename a socket:** tap a plug's row to open its detail modal (same UX as the AC-unit rename). The custom label is saved via `PUT /api/tuya/{id}/display_name` to a gitignored `config/tuya_display_names.json` (`device_id` → label, parallel to the unit `config/display_names.json`); a missing file is not an error. The override wins over the Tuya device name everywhere in the UI. The modal also shows the **original Smart Life name** (so a renamed device can be matched back to the app) and a **Hidden** toggle — the display name and Hidden edits commit together only on **Save** (closing discards them).
- **Hide a socket or blind:** the detail-modal **Hidden** toggle drops a device out of both lists; a **"Show hidden (N)"** button in the Plugs group's footer reveals them. Hidden state persists via `PUT /api/tuya/{id}/hidden` to a gitignored `config/tuya_hidden.json` (`device_id` → hidden marker, parallel to `config/network_hidden.json` / `config/security_hidden.json`); `GET /api/tuya` overlays the `hidden` flag per card.
- **Add a newly-paired device — and recover a stale one:** tap **Add device** in the Plugs group's footer, the in-app replacement for a `tinytuya wizard` terminal run. Pair the plug in the Smart Life app, tap the button, confirm, and it appears in the Plugs group. It runs **two** steps because the cloud and the LAN each know half the story: `src/tuya_cloud.py` calls the Tuya Cloud for the account's device list — the only place a device's **local key** and DPS mapping can come from — then runs a TinyTuya UDP broadcast scan (no cloud, no keys) that finds the **current** IP of every powered-on plug and reconciles those addresses into `devices.json` by device id. The scan is **unconditional**, so this is also the **DHCP-churn self-heal**: a plug that merely took a new lease becomes controllable again from the same button. Confirmed before it runs and never on a page load or poll tick — a cloud round trip plus an ~8 s scan is not a background cost; the button shows **Syncing…** while it works and reports exactly what it added and recovered. The sync is **non-destructive**: the cloud is authoritative only for identity and capability (key, mapping, name, category, model, MAC/UUID/SN), while `ip`, `version`, and any captured `dps` block on an existing row are preserved. That merge is `tuya_cloud.py`'s reason to exist — persisting TinyTuya's own `getdevices()` output instead would rebuild "changed" rows from a field whitelist with no `ip`, which on this repo's real `devices.json` dropped the stored address of 4 of the 7 devices that had one.- **Endpoints:** `GET /api/tuya` (device cards with switch state, reachability, live energy fields, the `display_name` override, and the `hidden` flag — the per-device LAN reads run in parallel), `POST /api/tuya/pair` (cloud sync + unconditional LAN rescan — the only rediscovery path; 503 with actionable text when credentials are missing or the IoT Core subscription expired), `POST /api/tuya/{id}/switch` (`{"on": true|false}`), `POST /api/tuya/{id}/cover` (`{"action": "open"|"close"|"stop"}` — 404 for a device that is not a blind, 502 when the blind did not answer, which is then retried), `POST /api/tuya/covers` (`{"action": …, "device_ids": [...]}` — omit `device_ids` for every blind; 200 with a per-blind `results` list (`ok`, `error`, `superseded`) even when some failed, 502 only when every blind failed, 400 for an unknown action or a device that is not a blind; failures are retried in the background), `POST /api/tuya/{id}/brightness` (`{"brightness": 1-100}` — 400 out of range or no brightness DPS, 502 on a LAN failure; answers with the read-back card), `PUT /api/tuya/{id}/display_name` (`{"display_name": "…"}`; empty clears the override), `PUT /api/tuya/{id}/hidden` (`{"hidden": true|false}`).
- **Cadence:** the tab refreshes every ~15 s **only while it is open** (LAN reads are comparatively expensive), and stops polling when you leave it.
- **Offline / stale-IP devices:** a powered-off plug or one without a usable LAN IP folds into the Plugs group's one **Offline** row (*2 plugs not reachable*) without blocking reachable devices from updating or being controlled; tap the row to list them under it (remembered per browser). The row says only *Not reachable right now*: the connection error and the setup hint stay off it.
- **Missing or stale devices?** Neither case needs a terminal — stale **IPs** and **new devices / rotated local keys** both arrive via **Add** (above). The TinyTuya CLI is only the first-ever bootstrap on a machine with no `devices.json` at all:

  ```powershell
  & .\.venv\Scripts\python.exe -m tinytuya wizard      # first-ever bootstrap only
  & .\.venv\Scripts\python.exe -m tinytuya snapshot    # quick IP/state refresh of known devices
  ```
