# Architecture — per-module reference

The exhaustive module-by-module inventory of the repository. The [README](../README.md#layout) carries the top-level directory map (what each directory *is*); this file is the detailed catalogue (what each file *does*). Keep the two in sync when a module is added, split, or removed — the README map is a dozen lines, this is the full list.

## `src/` — non-UI Python

- `melcloud_client.py` — async auth + fetch + control (the shared core).
- `list_devices.py` — CLI that prints each unit's live state.
- `huawei_client.py` — async read of the solar/energy flow (SUN2000 inverter + its RS485 power sensor). `fetch_energy_state()` tries `huawei_modbus.py` first and falls back to the **FusionSolar cloud** on any failure (issue #618), logging the serving source whenever it changes. The cloud remains the sole source for `fetch_energy_day()` (history backfill — the registers are instantaneous) and for today's cumulative kWh counters. Its `meterActivePower` is positive when **importing**, split into `grid_import_w` / `grid_export_w` in exactly one place.
- `huawei_modbus.py` — async read of the same flow **locally**, over Modbus TCP through the SDongleA-05 smart dongle (issue #618): ~1 s resolution against the cloud's 5-minute grid. `fetch_modbus_state()` returns `None` for every failure mode (unconfigured, unreachable, moved, rebooting) so the caller falls back cleanly; it never raises. Register `37113` is positive when **exporting** — the *opposite* of the cloud, proven live, and split in exactly one place here, never a shared helper. PV comes from `32080` (inverter AC output), not `32064` (DC input), so the flow balances at the meter. The dongle tolerates **one client at a time**, so reads are lock-serialised, the session is closed every cycle, and one snapshot is reused for `HUAWEI_MODBUS_CACHE_TTL_S` (default 5 s). It holds a DHCP lease and moves, so a failed read re-resolves it by MAC via `network_client.resolve_ip_by_mac` — the same pattern `camera_client.py` uses — before conceding to the cloud.
- `list_energy.py` — CLI that prints the live energy flow, and (at `INFO`) which of the two sources served it.
- `athom_client.py` — async read of **per-circuit** power from Athom BL0906 CT-clamp meters (issue #25), the complement to `huawei_client.py`'s whole-home figure. Meters are discovered over mDNS (`_esphomelib._tcp.local.`, filtered to Athom energy monitors by their advertised `package_import_url` / `project_name`) so a new meter needs no registration; `ATHOM_METER_HOSTS` is the static fallback. One SSE snapshot per meter replaces 21+ per-sensor REST calls. Every channel the meter has is returned whether or not a clamp is fitted, with `None` (not measured) kept distinct from a real `0.0`. An empty mDNS sweep never deletes a known meter — measured 1 miss in 20 cold browses, so "found nothing" is treated as unproven and the previous list is kept.
- `circuit_prefs.py` — per-channel prefs for those meters, keyed `"<meter_id>:<channel>"` (and the bare meter id for the meter itself): the custom label, an `invert` flag correcting a CT clamp fitted backwards, and a `hidden` flag putting an unused terminal away in the card (#619). Unlike the flat `id → name` rename stores below, the value is an object, since a channel carries several facts; persisted atomically to `config/circuit_prefs.json` (gitignored, `…sample.json` committed). Hiding is presentation only — the API keeps returning every channel, flagged.
- `list_circuits.py` — CLI that prints every discovered meter and all of its channels.
- `energy_history.py` — SQLite store + rollups for the energy dashboard history. Connection mechanics come from `_sqlite.py`.
- `telemetry.py` — unified event + reading store (SQLite; #283/#289). Narrow `readings`/`events` tables with JSON sidecars; producers (alarm/power/presence/plug/RISCO) mirror their events in, the Home **Activity log** reads them back. Connection mechanics come from `_sqlite.py`.
- `hvac_automation.py` — UI-free persistence + control law for per-unit dynamic temperature rules and daily schedules.
- `tariff.py` — electricity tariff model: prices grid energy per time-of-use period and values self-consumed PV (the cost & savings breakdown). UI-free, graceful flat-rate default.
- `tuya_client.py` — Smart Life / Tuya discovery and local LAN control foundation.
- `tuya_cloud.py` — the one Tuya path that leaves the LAN (issue #612): the in-app replacement for a `python -m tinytuya wizard` terminal run, driving `tinytuya.Cloud` directly (no subprocess, no QR — the QR is a one-time account link at iot.tuya.com) to capture a newly-paired device's identity, local key and DPS mapping into `devices.json`. Credentials come from `.env` (`TUYA_API_KEY`/`TUYA_API_SECRET`/`TUYA_REGION`), passed explicitly rather than via TinyTuya's own `tinytuya.json`. Kept out of `tuya_client.py` so that module's LAN-only-at-runtime contract stays true; it only ever runs behind the confirmed **Add** action (which also absorbed the retired Refresh button's LAN rescan, so that scan is now unconditional). `_merge_cloud_rows()` treats the cloud as authoritative for identity/capability only and preserves `ip`/`version`/`dps` — persisting TinyTuya's own `getdevices()` return value instead is lossy (its `filter_devices()` rebuilds "changed" rows from a whitelist with no `ip`, measured as dropping 4 of 7 stored LAN addresses on the real file).
- `ups_client.py` — local USB UPS status reader: prefers NUT (`upsc` against the portable Windows install), falls back to a one-shot NUT USB-HID probe, then Windows `Win32_Battery`.
- `host_shutdown.py` — thin wrapper over Windows `shutdown.exe`: `initiate_shutdown()` schedules a graceful shutdown with a grace window, `cancel_shutdown()` aborts a pending one. Hard-blocked under pytest so tests can never trigger a real shutdown. Used by the UPS low-battery safety trigger (see `power_monitor.py`).
- `searxng_client.py` — status + start control for the **SearXNG** container behind the voice assistant's Tier-3 web search (issue #321). UI-free; shells out to `docker` for the single `searxng` container (the compose stack itself lives in the sister `local-llm-hub` repo, path from `SEARXNG_COMPOSE_PATH`) and probes `SEARXNG_URL`'s `/healthz` so "container up" stays distinguishable from "actually answering queries". Same "shell out, flatten, partial data stays 200" shape as `hyperv_client.py` / `ups_client.py`, `NO_WINDOW` included. `fetch_searxng_state()` never raises — a missing container, a stopped one, or an unreachable `/healthz` each come back as an `available=False` `SearxngState` with a distinct `error`; `start_searxng()` raises `SearxngConfigError` / `SearxngCommandError` instead, so the router can map each cause to its own HTTP status.
- `hyperv_client.py` — status + lifecycle control for the Home Assistant Hyper-V VM (#240): shells out to `Get-VM` / `Start-VM` / `Stop-VM` for the single VM named by `HA_VM_NAME` (by name only — never any other VM), returning a flattened `HyperVState` (state, uptime, IP, MAC). Distinct errors for missing name / not-found / insufficient rights / already-in-state; graceful ACPI stop only.
- `ha_client.py` — UI-free async HA REST/WebSocket client (#239): discovers Assist satellites through HA-owned entity/device/area registries, joins companion media-player volume, announces to one satellite, calls an arbitrary HA service against one entity (`call_service()`, e.g. `climate.turn_on` — issue #641's AC on/off action), and reads the bounded Assist pipeline debug surface; includes the pure raw-trace → compact-interaction normalizer.
- `voice_client.py` — async Voice Transcriber session-API client (#239): attributed create, one-second raw chunk append, SSE pass-through, finish, and single-shot fallback. It never owns audio/model persistence; Voice Transcriber does.
- `elgato_client.py` — Elgato lights discovery/read/control over the local LAN HTTP API.
- `_atomic_json.py` — shared atomic write-tmp + `os.replace` primitives (`atomic_write_bytes` / `write_json_atomic`; issue #327), the single implementation behind the pattern that used to be copy-pasted across 18 `src/` modules.
- `_no_window.py` — single home for the Windows "don't flash a console window" spawn flag (`NO_WINDOW`; issue #572), the one constant every `subprocess` call site in `src/`, `app/` and `scripts/` passes as `creationflags`. `0` off Windows, which POSIX `subprocess` accepts, so no call site needs a platform branch. Replaces three incompatible spellings (module-level ternary, inline `kwargs[...]` under a `sys.platform` guard, `getattr(subprocess, …)`) that had already let `scripts/gen_tailscale_cert.py` drift unflagged.
- `_sqlite.py` — shared WAL-mode SQLite `connect()` context manager (issue #452), the single implementation behind the pragma/`mkdir`/`Row`-factory shape that used to be copy-pasted byte-for-byte across `energy_history.py`, `network_history.py`, and `telemetry.py`.
- `_schedule_store.py` — shared read/save + `safe_id`/`clean_time`/`clean_days` helpers for weekly schedule-entry stores (issue #327), deduping `security_schedules.py` and `wake_alarms.py` (`hvac_automation.py` reuses the read/save pair too); built on `_atomic_json.py`.
- `_toggle_prefs.py` — parametrized load/save for frozen bool-toggle-dataclass prefs stores (issue #327), deduping `alarm_notify_prefs.py` and `power_notify_prefs.py`; built on `_atomic_json.py`.
- `_spoken_time.py` — single home for the spoken date/time cue grammar (`fmt_time` / `extract_time` / `extract_date` / `WEEKDAY_WORDS`; issue #571), deduping the ~50 verbatim lines `reminders.py` and `calendar_events.py` each carried. Pure parsing, no I/O; `wake_alarms.py` keeps its own richer bilingual parser, which is a different grammar rather than a copy.
- `risco_client.py` — async RISCO Cloud alarm state (incl. system AC-power + per-zone trouble flags), controls, event log, and detector bypass. Merges the pyrisco Cloud status with `risco_webui.py`'s scraped state flags.
- `risco_webui.py` — the native RISCO WebUI HTML/JSON scraper (site login, arm/disarm command, raw state-flags read) that `risco_client.py` layers on top of — split out in #328 to keep this brittle, screen-scraped path (the source of the false-intrusion bug fixed in #307) visually separate from the typed cloud fetcher.
- `security_schedules.py` — UI-free persistence and due-window checks for weekly alarm schedules; read/save + field-cleaning via `_schedule_store.py`.
- `wake_alarms.py` — UI-free persistence + due-window checks for **wake alarms** (recurring day-of-week or one-shot date; Alexa-style, ring/notify only — never touches the RISCO security alarm), plus the voice helpers `parse_spoken_alarm` (spoken time/schedule → entry) and `describe_alarm` (speakable summary) — both bilingual via a `lang="es"` branch that parses/speaks Spanish times ("las siete y media entre semana", #466) — and `next_fire`/`soonest_enabled`, used by the voice API (#306). Shares `security_schedules.py`'s read/save + field-cleaning via `_schedule_store.py`; `config/wake_alarms.json`.
- `wake_timers.py` — in-memory (unpersisted) countdown-**timer** store; mirrors Home Assistant's own ephemeral voice timers (a restart clears them). Create/list/cancel + `mark_expired`.
- `reminders.py` — UI-free persistence for free-text **reminders** (issue #314): a `ReminderEntry` (text, `done`, optional due `date`/`time`, `created_at`), bidirectional between the PWA and Voice PE (either surface writes into the same list). `parse_spoken_reminder` splits a spoken phrase's due-date/time cue ("at 6pm", "tomorrow", "on friday") off the reminder text via the shared `_spoken_time.py` grammar; `describe_reminder` renders a speakable summary; `soonest_pending`/`next_due` resolve "the next one" for voice complete (earliest-due first, then FIFO among undated entries). English only — unlike `wake_alarms.py`, no Spanish parsing/speech branch. `config/reminders.json`.
- `calendar_events.py` — UI-free, pure parsing/shaping for voice-created **Google Calendar events** (issue #313), no local persistence (Google Calendar is the only store). `parse_spoken_calendar_event` splits a trailing due-date/time cue and embedded "to my calendar" filler off the phrase (cue grammar shared with `reminders.py` via `_spoken_time.py`); unlike a reminder, a calendar event needs a date to be meaningful, so neither-date-nor-time returns `None`. `to_google_event_body` shapes the parsed dict into a Google Calendar API v3 event body (all-day vs. timed with an IANA `timeZone`); `describe_calendar_event` renders the speakable confirmation.
- `calendar_write.py` — the only module importing Google libraries: an installed-app OAuth2 write client for the Google Calendar API, scoped to `calendar.events` only (insert/update/delete — no calendar-list/ACL read). Adapted from the same pattern whatsapp-radar's #217 built for the same problem. `insert_event` is create-only (no delete/update — this issue has no cancel/edit acceptance criterion). The token is bootstrapped once via `scripts/auth_calendar_write.py`; `config/calendar_write_token.json` (gitignored, no committed sample — it's an OAuth token, not a config schema).
- `voice_commands.py` — the curated catalogue of every wired Voice PE command (#437), grouped by feature and tagged per language/wake word ("Okay Nabu" English, "Hey Mycroft" Spanish; the alarm + wake-alarm groups are bilingual since #466, which also added the card's EN/ES filter toggle), served to the PWA's "What can I say?" card by `routers/voice_commands.py`. Static prose, no I/O and no secrets (the disarm code is only ever the `<your code>` / `<tu código>` placeholder `docs/voice-pe-config/README.md` already publishes). Curated rather than derived from `custom_sentences/*.yaml` because those are hassil templates and don't cover the multi-turn grocery automation or the HA built-ins; the cost — a second place to update — is paid by step 6 of `docs/voice-commands-howto.md`'s recipe.
- `presence_client.py` — read-only iCloud Find My spike client for location/presence feasibility; `load_presence_configs()` reads one or two Apple Accounts (`ICLOUD_EMAIL[_2]`) and `fetch_presence()` normalizes each account's devices, so two phones on separate Apple IDs merge into one snapshot (issue #478); `begin_trust_renewal()` / `complete_trust_renewal()` renew Apple's ~30-day browser trust on one live session and swap it into the cached-session map (issue #659).
- `device_address.py` — the "pin a device by MAC instead of IP" resolver (issue #504; README "Pin a device by MAC instead of IP"). A config value that already looks like an IP or hostname is returned untouched with **no network call at all**, so no existing config has to change and the common path costs nothing; only a MAC-shaped value (`is_mac()`, anchored six-hex-pair regex so an IPv6 literal or a hex-ish hostname can never match) triggers a lookup through `network_client.resolve_ip_by_mac`. Two behaviours make it safe in front of a live device call: a short-TTL cache (`RESOLVE_TTL_S`, 120 s) so a burst of calls resolves once, and a **last-known-good fallback** — a failed inventory read returns the previously resolved address rather than raising, since a resolver that hard-fails while the router is briefly unreachable would be strictly worse than the hardcoded IP it replaces. `resolve_device_host()` (async) / `resolve_device_host_sync()` (for `scripts/ha_config_sync.py`) take a bare host; `resolve_url_host()` swaps only a URL's host, because a MAC's colons collide with the port separator and cannot sit in a URL (`HA_HOST_MAC` + `HA_URL`, used by `ha_client.py`).
- `network_client.py` — async home-network orchestrator (issue #197 split): imports the three sub-modules below and exposes the unchanged public surface (`fetch_network_state`, `resolve_ip_by_mac`, `resolve_wireless_client_by_mac`, dataclasses) so callers don't move. `resolve_wireless_client_by_mac` (issue #547) backs the walk test: it reads the AP **and** the router concurrently and runs the same client merge the full snapshot uses, because the AP reports a client of the router's radio as `wired` at 100% (an uplink artefact) — an AP-only lookup would fabricate that reading into every sample.
- `network_types.py` — shared dataclasses, exceptions, and leaf helpers used across all network sub-modules.
- `network_ap.py` — NETGEAR R9000 AP: device inventory (MAC/IP/name/signal/band/SSID), AP health, `reboot_access_point`, MAC rediscovery.
- `network_router.py` — Vodafone ZXHN F6600P (ZTE): SHA256-challenge login, WAN/DHCP reads, its own radios' wireless-client read (the only source for clients attached to the router rather than the AP), binding write-back, `reboot_router`.
- `network_host.py` — host-side internet probes: ping latency + packet loss, optional speedtest, `netsh wlan`.
- `list_network.py` — CLI that prints the live network state and inventory.
- `dhcp_plan.py` — UI-free, network-free DHCP reservation planner (#170): classifies each device into a category range from `config/dhcp_plan.json` and assigns the lowest free IP, anchoring stability on the router's existing bindings and tagging each row reserved/create/change; warns on overflow/overlap/unclassified/randomised-MAC.
- `list_dhcp_plan.py` — CLI that prints the categorised reservation plan (mirrors `list_network.py`); `--apply` pushes the create/change rows to the router (#176) behind a `yes` prompt.
- `network_display_names.py` / `network_wifi_display_names.py` / `network_hidden.py` — Network-tab label and hidden-state stores for attached devices and Wi-Fi radios; reuse `display_names.py` atomic load/save/set verbatim, parallel to the unit/plug/detector stores. `network_hidden.py` covers both attached-device (`config/network_hidden.json`) and Wi-Fi radio (`config/network_wifi_hidden.json`) hidden state in one module.
- `network_groups.py` — user-defined display groups for attached devices (#513): normalised MAC → group name in gitignored `config/network_groups.json`, reusing the same `display_names.py` atomic helpers as the stores above, plus bulk `rename_network_group` / `delete_network_group`. Groups exist only as the set of assignments, so an empty group cannot exist and unassigned devices fall into the UI's synthetic trailing "Unclassified". Display-only and deliberately independent of `dhcp_plan.py`'s IP-range categories.
- `network_oui.py` — offline device identification: bundled trimmed OUI→vendor table, randomised-MAC detection, and a category/icon heuristic (no network call, render-time).
- `network_history.py` — per-MAC history store (SQLite, modeled on `energy_history.py`; issue #129 Phase 4): first/last/times-seen, the last-known IP/hostname/band/SSID, the `important` flag, and the online/offline + new-device derivations. Columns added after it shipped are topped up by an idempotent `ALTER TABLE` sweep in `init_db`. Recorded on each `/api/network` read (no background sampler — the AP read is expensive and tab-gated); randomised MACs are never tracked. Kept separate from the rename/hidden stores; gitignored `webapp/network_history.sqlite3`. Connection mechanics come from `_sqlite.py`.
- `network_survey.py` — Wi-Fi walk-test sample store (SQLite, sibling of `network_history.py`; issue #547): one append-only row per user-initiated coverage sample — room label, client MAC, the AP/router-measured signal/link-rate/band/SSID and which box reported it, plus the browser-measured RTT/jitter/loss/throughput. A MAC on neither radio is stored as `source='not_found'` with a null signal so "no coverage here" stays a distinguishable state rather than a blank. Deliberate user writes only (no poll, unlike the history store); 365-day retention pruned on write; gitignored `webapp/network_survey.sqlite3`. Connection mechanics come from `_sqlite.py`.
- `dhcp_overrides.py` — per-MAC category overrides chosen in the Network tab UI; persisted to gitignored `config/dhcp_overrides.json` and merged over `config/dhcp_plan.json` by the planner so a UI choice wins without editing the committed config.
- `camera_client.py` — async, UI-free camera core (issue #161): ONVIF for discovery/profiles/PTZ (`ContinuousMove` / `Stop` / `AbsoluteMove`, preset management), RTSP + ffmpeg for snapshot / MJPEG stream / clip recording. Returns a flattened `CameraInfo` per declared camera; capabilities (`ptz_presets`, `ptz_absolute`, `ptz_relative`) gate the UI controls. Cameras declared in gitignored `config/cameras.json`.
- `camera_ffmpeg.py` — ffmpeg subprocess wrapper used by `camera_client.py` for RTSP→JPEG snapshot, RTSP→MJPEG stream transcoding, and server-side mp4 recording. Every ffmpeg call is dispatched to a lazily-started background thread running its own persistent `ProactorEventLoop` (issue #399) — Windows only supports `asyncio` subprocess transports on the proactor loop, but the webapp's own uvicorn loop is the selector loop (issue #397's fix for the accept-loop wedge), so ffmpeg calls can't run directly on the server's own loop.
- `camera_display_names.py` — custom label store for camera IDs; parallel to `display_names.py`; persisted to gitignored `config/camera_display_names.json`.
- `camera_presets.py` — software PTZ preset store for cameras that lack native ONVIF preset support; persisted to gitignored `config/camera_presets.json` (absolute pan/tilt/zoom coordinates).
- `camera_preset_names.py` — custom label store for camera preset tokens, keyed by `"camera_id::token"`; persisted to gitignored `config/camera_preset_names.json` via `display_names.py`'s atomic load/save (issue #452), only the composite key and on-disk path differ.
- `pv_forecast.py` — Open-Meteo global-tilted-irradiance → expected-generation forecast engine (issue #39): one keyless API call per sub-array for yesterday/today/tomorrow; scales hourly GTI by kWp × performance_ratio. `fetch_pv_forecast_for_date()` (issue #590) runs the same model against an arbitrary date by widening the request's `past_days`; the three named days always resolve to `past_days=1`, so the forecast card's request and answer are unchanged. Carries an optional PVWatts-style panel-temperature derate (issue #591, `thermal_model_enabled`, **off by default**): NOCT cell temperature from `temperature_2m` fetched in the same request, scaled by γ = −0.0035/°C. Also carries an optional horizon/shading term (issue #578 part b, `horizon_profile_enabled`, **off by default**): reuses `sun_position()` per hour to attenuate the direct-beam share (estimated from `direct_radiation`/`diffuse_radiation`, fetched only when armed) whenever the sun sits at or below a hand-entered obstruction elevation for its azimuth. UI-free; read by `GET /api/energy/forecast` and `GET /api/energy/sun-overlay`.
- `sun_position.py` — solar azimuth + elevation from an instant and the home's coordinates (issue #590), via NOAA's low-precision algorithm. Stdlib-only (no new dependency) and pure — no clock, config or I/O of its own. Azimuth is clockwise from true north, elevation geometric (no refraction term, which only matters at the horizon the diagnostic already excludes). UI-free; the x-axis of the read-only measured-vs-modelled overlay, and reused by `pv_forecast.py`'s horizon-shading term (issue #578 part b).
- `pv_system_config.py` — PV array config loader (`config/pv_system.json`): kWp, tilt, azimuth, performance ratio, the off-by-default `thermal_model_enabled` switch, and the off-by-default `horizon_profile`/`horizon_profile_enabled` pair (issue #578 part b — compass-from-north azimuth, deliberately not `arrays[].azimuth_deg`'s Open-Meteo convention). Missing file returns a disabled sentinel rather than an error. `thermal_migration_error()` is the single place that names the one combination the thermal settings must never form (the temperature term armed over an un-migrated combined `performance_ratio`) — the strict writer raises it, the forecast refuses to compute on it.
- `location_config.py` — home-location config loader (`config/location.json`): lat/lon/optional label used by the weather and PV-forecast endpoints. Missing file surfaces as `configured=False` with HTTP 200 — never a 500.
- `travel_time.py` — traffic-aware driving duration to home via the Google **Routes API** (`directions/v2:computeRoutes`; issues #470/#472 — the legacy Directions API is deprecated), behind the voice "how long to get home?" follow-up. `fetch_travel_time()` POSTs with `routingPreference: TRAFFIC_AWARE` (defaults departure to now); `_parse_routes()` maps `routes[0].duration`. UI-free and degrade-gracefully like the locator: a missing `GOOGLE_MAPS_API_KEY`, an unreachable API, or no route returns `available=False` with a machine `reason`, never raises.
- `elgato_display_names.py` — custom label store for Elgato lights; keyed by MAC address when available (survives DHCP changes), with a legacy host:port fallback; persisted to gitignored `config/elgato_display_names.json`.
- `tuya_hidden.py` — hidden-state store for Tuya plugs/blinds; persisted to gitignored `config/tuya_hidden.json`; parallel to `network_hidden.py` and `security_hidden.py`.
- `security_hidden.py` — hidden-state store for RISCO detectors; persisted to gitignored `config/security_hidden.json`.
- `security_trouble_ignore.py` — per-zone trouble-ignore store; persisted to gitignored `config/security_trouble_ignore.json`; a muted zone is dropped from the main-card trouble count while still showing `Trouble — ignored` in the list.
- `security_override.py` — per-zone "bypass after N repeated alarms this armed session" rule store (issue #341, `max_retries` clamped to 1-3); persisted to gitignored `config/security_override.json`.
- `security_override_session.py` — persisted scan cursor + per-zone trigger counts + auto-bypassed-zone tracking for `security_override_automation.py`, so a restart mid-session doesn't lose count; persisted to gitignored `config/security_override_session.json`.
- `presence_display_names.py` — custom label store for presence person IDs; parallel to `display_names.py`; persisted to gitignored `config/presence_display_names.json`.
- `presence_hidden.py` — hidden-state store for Find My / presence entities; persisted to gitignored `config/presence_hidden.json`.
- `presence_engine.py` — webhook-backed presence state and alarm-transition decision engine: reads `config/presence_state.json`, evaluates grace-period / Kids-home logic, and drives arm/disarm; appends a JSONL audit row to gitignored `logs/presence_triggers.jsonl`.
- `presence_places.py` — the "where's mom/dad" voice locator's named-place store (issue #438): `PresencePlace` dataclass (`id`/`label`/`lat`/`lon`/`radius_m`), whole-list CRUD (modeled on `security_schedules.py`) persisted to gitignored `config/presence_places.json`, and `resolve_place()` — the closest configured place within its radius wins, else "Home"/"Away"/unknown from cached distance-from-home data (no new iCloud locate cost).
- `presence_roles.py` — household-role alias store (e.g. "dad"/"mom" → a person/entity id) for the same locator; reuses `display_names.py`'s atomic store verbatim (like `presence_display_names.py`), persisted to gitignored `config/presence_roles.json`; `resolve_person()` matches a spoken name/role case-insensitively against roles, display names, then raw names.
- `push_notifications.py` — best-effort Web Push sender for presence transitions: reads VAPID keys + subscriptions from gitignored `config/push_config.json` / `config/push_subscriptions.json`; silent no-op when not configured.
- `notify/` — the universal Telegram notifier vendored verbatim from `project-scaffolding` (`TelegramNotifier` + `NotifierError` + `TelegramConfig` + `build_notifier`); `notify_config.py` wires the app's gitignored `config/notify_config.json` / `TELEGRAM_*` env to it (`build_alarm_notifier()` → notifier or silent no-op).
- `activity_log.py` — reusable append-only JSONL activity log; `append_activity(consumer, event)` writes one timestamped line to gitignored `logs/<consumer>.jsonl`. Used for `logs/alarm.jsonl` (every arm/disarm command + result) and delegated to by the presence trigger log.
- `alarm_notify_prefs.py` — seven per-event toggles for alarm Telegram alerts (arm/disarm successes default off; `error`/`intrusion`/`ac_lost` default on), persisted to gitignored `config/alarm_notify_prefs.json` via `_toggle_prefs.py`.
