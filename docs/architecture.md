# Architecture — per-module reference

The exhaustive module-by-module inventory of the repository. The [README](../README.md#layout) carries the top-level directory map (what each directory *is*); this file is the detailed catalogue (what each file *does*). Keep the two in sync when a module is added, split, or removed — the README map is a dozen lines, this is the full list.

## `src/` — non-UI Python

Domain modules live in subpackages — `src/security/`, `src/presence/`, `src/network/`, `src/energy/`, `src/devices/`, `src/voice/` — and the shared helpers, cross-domain stores and `list_*` CLIs stay at the top of `src/` ([layout](layout.md)). Entries below are listed by file name.

- `melcloud_client.py` — async auth + fetch + control (the shared core).
- `list_devices.py` — CLI that prints each unit's live state.
- `huawei_client.py` — async read of the solar/energy flow (SUN2000 inverter + its RS485 power sensor). `fetch_energy_state()` tries `huawei_modbus.py` first and falls back to the **FusionSolar cloud** on any failure, logging the serving source whenever it changes. The cloud remains the sole source for `fetch_energy_day()` (history backfill — the registers are instantaneous) and for today's cumulative kWh counters. Its `meterActivePower` is positive when **importing**, split into `grid_import_w` / `grid_export_w` in exactly one place.
- `huawei_modbus.py` — async read of the same flow **locally**, over Modbus TCP through the SDongleA-05 smart dongle: ~1 s resolution against the cloud's 5-minute grid. `fetch_modbus_state()` returns `None` for every failure mode (unconfigured, unreachable, moved, rebooting) so the caller falls back cleanly; it never raises. Register `37113` is positive when **exporting** — the *opposite* of the cloud, proven live, and split in exactly one place here, never a shared helper. PV comes from `32080` (inverter AC output), not `32064` (DC input), so the flow balances at the meter. The dongle tolerates **one client at a time**, so reads are lock-serialised, the session is closed every cycle, and one snapshot is reused for `HUAWEI_MODBUS_CACHE_TTL_S` (default 5 s). It holds a DHCP lease and moves, so a failed read re-resolves it by MAC via `network_client.resolve_ip_by_mac` — the same pattern `camera_client.py` uses — before conceding to the cloud.
- `list_energy.py` — CLI that prints the live energy flow, and (at `INFO`) which of the two sources served it.
- `athom_client.py` — async read of **per-circuit** power from Athom BL0906 CT-clamp meters, the complement to `huawei_client.py`'s whole-home figure. Meters are discovered over mDNS (`_esphomelib._tcp.local.`, filtered to Athom energy monitors by their advertised `package_import_url` / `project_name`) so a new meter needs no registration; `ATHOM_METER_HOSTS` is the static fallback. One SSE snapshot per meter replaces 21+ per-sensor REST calls. Every channel the meter has is returned whether or not a clamp is fitted, with `None` (not measured) kept distinct from a real `0.0`. An empty mDNS sweep never deletes a known meter — measured 1 miss in 20 cold browses, so "found nothing" is treated as unproven and the previous list is kept.
- `circuit_prefs.py` — per-channel prefs for those meters, keyed `"<meter_id>:<channel>"` (and the bare meter id for the meter itself): the custom label, an `invert` flag correcting a CT clamp fitted backwards, and a `hidden` flag putting an unused terminal away in the card. Unlike the flat `id → name` rename stores below, the value is an object, since a channel carries several facts; persisted atomically to `config/circuit_prefs.json` (gitignored, `…sample.json` committed). Hiding is presentation only — the API keeps returning every channel, flagged.
- `list_circuits.py` — CLI that prints every discovered meter and all of its channels.
- `energy_history.py` — SQLite store + rollups for the energy dashboard history. Connection mechanics come from `_sqlite.py`.
- `telemetry.py` — unified event + reading store (SQLite). Narrow `readings`/`events` tables with JSON sidecars; producers (alarm/power/presence/plug/RISCO) mirror their events in, the Home **Activity log** reads them back. A third table, `rollup_hourly`, folds each completed hour of `readings` into one row per `(hour, domain, entity, metric)` before the 7-day raw prune, so no metric's history stops at a week; it records `covered_s` (how much of the hour the aggregate rests on, the `energy_history` discipline) and resolves categorical metrics to last-value-plus-change-count rather than averaging them. Connection mechanics come from `_sqlite.py`.
- `hvac_automation.py` — UI-free persistence + control law for per-unit dynamic temperature rules and daily schedules.
- `blind_automation.py` — UI-free blind group control: `move_blinds()` sends one open/stop/close to every blind (or a named subset) **in parallel** over `tuya_client.set_cover`, returning a per-blind outcome so one offline blind never stops the rest; `cover_device_ids()` is the "every blind" set, the same cover-DPS test as the `has_cover` card flag. `retry_failed_blinds()` (manual taps) re-sends only a move's failed blinds on a 30/60/120/240 s backoff (2/4/8 s for a Stop) with an injectable sleep, dropping a blind once `note_blind_command()` has numbered a newer command to it (manual taps, schedules and alarm moves all number theirs). Sends to one blind are serialised by a per-blind lock that re-checks the command is still the newest before sending, so commands land in tap order. Also the daily blind-schedule store: `BlindScheduleEntry` (time, weekdays, open/close, target blinds, presence condition) persisted to gitignored `config/blind_schedules.json` through `_schedule_store`, plus `presence_allows()`, which keeps "no tracked people" as its own unknown state. And the alarm pairing: `alarm_blind_action()` (close on a confirmed full arm, open on a confirmed daytime disarm, nothing on perimeter/partial), `is_daytime()` (the schedule's earliest-Up-to-latest-Down day, else sun elevation, else unknown) and the `follow_alarm` switch in gitignored `config/blind_alarm.json`.
- `tariff.py` — electricity tariff model: prices grid energy per time-of-use period and values self-consumed PV (the cost & savings breakdown). UI-free, graceful flat-rate default.
- `tuya_client.py` — Smart Life / Tuya discovery and local LAN control foundation. Blind cover types are learned from status reads and persisted to gitignored `config/tuya_cover_types.json`.
- `tuya_cloud.py` — the one Tuya path that leaves the LAN: the in-app replacement for a `python -m tinytuya wizard` terminal run, driving `tinytuya.Cloud` directly (no subprocess, no QR — the QR is a one-time account link at iot.tuya.com) to capture a newly-paired device's identity, local key and DPS mapping into `devices.json`. Credentials come from `.env` (`TUYA_API_KEY`/`TUYA_API_SECRET`/`TUYA_REGION`), passed explicitly rather than via TinyTuya's own `tinytuya.json`. Kept out of `tuya_client.py` so that module's LAN-only-at-runtime contract stays true; it only ever runs behind the confirmed **Add** action (which also absorbed the retired Refresh button's LAN rescan, so that scan is now unconditional). `_merge_cloud_rows()` treats the cloud as authoritative for identity/capability only and preserves `ip`/`version`/`dps` — persisting TinyTuya's own `getdevices()` return value instead is lossy (its `filter_devices()` rebuilds "changed" rows from a whitelist with no `ip`, measured as dropping 4 of 7 stored LAN addresses on the real file).
- `ups_client.py` — local USB UPS status reader: prefers NUT (`upsc` against the portable Windows install), falls back to a one-shot NUT USB-HID probe, then Windows `Win32_Battery`.
- `host_shutdown.py` — thin wrapper over Windows `shutdown.exe`: `initiate_shutdown()` schedules a graceful shutdown with a grace window, `cancel_shutdown()` aborts a pending one. Hard-blocked under pytest so tests can never trigger a real shutdown. Used by the UPS low-battery safety trigger (see `power_monitor.py`).
- `searxng_client.py` — status + start control for the **SearXNG** container behind the voice assistant's Tier-3 web search. UI-free; shells out to `docker` for the single `searxng` container (the compose stack itself lives in the sister `local-llm-hub` repo, path from `SEARXNG_COMPOSE_PATH`) and probes `SEARXNG_URL`'s `/healthz` so "container up" stays distinguishable from "actually answering queries". Same "shell out, flatten, partial data stays 200" shape as `hyperv_client.py` / `ups_client.py`, `NO_WINDOW` included. `fetch_searxng_state()` never raises — a missing container, a stopped one, or an unreachable `/healthz` each come back as an `available=False` `SearxngState` with a distinct `error`; `start_searxng()` raises `SearxngConfigError` / `SearxngCommandError` instead, so the router can map each cause to its own HTTP status.
- `hyperv_client.py` — status + lifecycle control for the Home Assistant Hyper-V VM: shells out to `Get-VM` / `Start-VM` / `Stop-VM` for the single VM named by `HA_VM_NAME` (by name only — never any other VM), returning a flattened `HyperVState` (state, uptime, IP, MAC). Distinct errors for missing name / not-found / insufficient rights / already-in-state; graceful ACPI stop only.
- `ha_client.py` — UI-free async HA REST/WebSocket client: discovers Assist satellites through HA-owned entity/device/area registries, joins companion media-player volume, announces to one satellite, calls an arbitrary HA service against one entity (`call_service()`, e.g. `climate.turn_on` — the AC on/off action), and reads the bounded Assist pipeline debug surface; includes the pure raw-trace → compact-interaction normalizer.
- `voice_client.py` — async Voice Transcriber session-API client: attributed create, one-second raw chunk append, SSE pass-through, finish, and single-shot fallback. It never owns audio/model persistence; Voice Transcriber does.
- `elgato_client.py` — Elgato lights discovery/read/control over the local LAN HTTP API.
- `_atomic_json.py` — shared atomic write-tmp + `os.replace` primitives (`atomic_write_bytes` / `write_json_atomic`), the single implementation behind the pattern that used to be copy-pasted across 18 `src/` modules.
- `_backoff.py` — shared exponential-backoff tracker for a persistently-failing source, deduping `ups_client.py`'s `_SourceBackoff` and `tuya_client.py`'s `_DeviceBackoff` (byte-identical constants and comment) plus `huawei_client.py`'s free-function `_backoff_for`/`_note_failure`/`_note_success` (own constants — a cloud login tolerates a different retry cadence than a local NUT/Tuya poll). `compute_delay()` is the pure escalate-with-cap math; `BackoffTracker` wraps it with `consecutive_failures`/`next_retry_at` state, used standalone (`ups_client.py`'s two per-source trackers; one each in `huawei_client.py` and `pv_forecast.py`) or in a per-key `dict` (`tuya_client.py`'s per-device map).
- `_no_window.py` — single home for the Windows "don't flash a console window" spawn flag (`NO_WINDOW`), the one constant every `subprocess` call site in `src/`, `app/` and `scripts/` passes as `creationflags`. `0` off Windows, which POSIX `subprocess` accepts, so no call site needs a platform branch. Replaces three incompatible spellings (module-level ternary, inline `kwargs[...]` under a `sys.platform` guard, `getattr(subprocess, …)`) that had already let `scripts/gen_tailscale_cert.py` drift unflagged.
- `_tailscale_binary.py` — single home for locating the `tailscale` CLI (`tailscale_binary()`): PATH first, then the standard Windows Program Files install dir, since the GUI installer doesn't always add it to PATH and both callers (the tray at login, the webapp boot path) can run with a minimal environment. Shared by `app/tray/tray.py` ("Copy Tailscale URL") and `scripts/gen_tailscale_cert.py`, which previously resolved the binary with a bare `shutil.which("tailscale")` and so missed the Program Files fallback the tray already had.
- `_env.py` — shared `.env` knob parsers (`_env_bool` / `_env_int` / `_env_float`), the single implementation of "blank → default, invalid → warn-and-default" for `src/` and (re-exported by `app/webapp/_env.py`) the webapp.
- `secret_compare.py` — `secrets_match()`, the constant-time secret comparison (UTF-8 bytes, so a non-ASCII password or token is a mismatch rather than a `TypeError` from `hmac.compare_digest`) used by login, the bearer middleware, the presence webhook and `camera_token.py`.
- `_sqlite.py` — shared WAL-mode SQLite `connect()` context manager, the single implementation behind the pragma/`mkdir`/`Row`-factory shape that used to be copy-pasted byte-for-byte across `energy_history.py`, `network_history.py`, and `telemetry.py`.
- `_schedule_store.py` — shared read/save + `safe_id`/`clean_time`/`clean_days`/`clean_date` helpers for weekly schedule-entry stores (`clean_date` added later, deduping `wake_alarms.py` and `reminders.py`'s byte-identical `_clean_date`), deduping `security_schedules.py` and `wake_alarms.py` (`hvac_automation.py` reuses the read/save pair too); built on `_atomic_json.py`. Also the list-of-dataclass store triple (`load_entry_list`/`clean_entry_list`/`save_entry_list`) that `reminders.py`, `presence_places.py`, `security_schedules.py`, `alarm_scene_config.py`, `security_override.py` and `wake_alarms.py` delegate their `load_*`/`save_*`/`set_*` to.
- `_toggle_prefs.py` — parametrized load/save for frozen bool-toggle-dataclass prefs stores, deduping `alarm_notify_prefs.py` and `power_notify_prefs.py`; built on `_atomic_json.py`.
- `_spoken_time.py` — single home for the spoken date/time cue grammar (`fmt_time` / `extract_time` / `extract_date` / `WEEKDAY_WORDS`), deduping the ~50 verbatim lines `reminders.py` and `calendar_events.py` each carried. Pure parsing, no I/O; `wake_alarms.py` keeps its own richer bilingual parser, which is a different grammar rather than a copy.
- `_console_encoding.py` — single home for the Windows native-console-tool decoding pin (`console_encoding()`), extracted from `network_host.py`'s `_console_encoding()` after `hyperv_client.py` and `ups_client.py` were found shelling out to `powershell.exe` with the same shape but no decoding pin — a function, not a constant, so tests can monkeypatch `sys.platform` per case.
- `usage_log.py` — the server half of the vendored usage log: `usage_router()` behind `POST /api/usage/events` + `GET /api/usage/summary`, storing views, taps and device class in the runtime-data `usage.sqlite3` (`USAGE_LOG_DB_PATH` overrides it). Vendor-verbatim from `project-scaffolding`.
- `compression.py` — `StreamSafeGZipMiddleware`, the stream-safe gzip layer registered last (outermost) in `server.py`: it gzips HTML, JS, CSS, JSON and SVG for a gzip client and passes event streams, MJPEG, other images, audio and bodyless responses through untouched. Vendor-verbatim from `project-scaffolding`.
- `runtime_data.py` — resolves where an always-on service's SQLite state lives (`runtime_data_dir()` / `runtime_db_path()`), instead of hardcoding it to wherever the repo happened to be checked out. Vendor-verbatim, like `_no_window.py`.
- `risco_client.py` — async RISCO Cloud alarm state (incl. system AC-power + per-zone trouble flags), controls, event log, and detector bypass. Merges the pyrisco Cloud status with `risco_webui.py`'s scraped state flags.
- `risco_webui.py` — the native RISCO WebUI HTML/JSON scraper (site login, arm/disarm command, raw state-flags read) that `risco_client.py` layers on top of — split out to keep this brittle, screen-scraped path (the source of the false-intrusion bug fixed) visually separate from the typed cloud fetcher.
- `security_schedules.py` — UI-free persistence and due-window checks for weekly alarm schedules; read/save + field-cleaning via `_schedule_store.py`.
- `wake_alarms.py` — UI-free persistence + due-window checks for **wake alarms** (recurring day-of-week or one-shot date; Alexa-style, ring/notify only — never touches the RISCO security alarm), plus the voice helpers `parse_spoken_alarm` (spoken time/schedule → entry) and `describe_alarm` (speakable summary) — both bilingual via a `lang="es"` branch that parses/speaks Spanish times ("las siete y media entre semana") — and `next_fire`/`soonest_enabled`, used by the voice API. Shares `security_schedules.py`'s read/save + field-cleaning via `_schedule_store.py`; `config/wake_alarms.json`.
- `wake_timers.py` — in-memory (unpersisted) countdown-**timer** store; mirrors Home Assistant's own ephemeral voice timers (a restart clears them). Create/list/cancel + `mark_expired`.
- `reminders.py` — UI-free persistence for free-text **reminders**: a `ReminderEntry` (text, `done`, optional due `date`/`time`, `created_at`), bidirectional between the PWA and Voice PE (either surface writes into the same list). `parse_spoken_reminder` splits a spoken phrase's due-date/time cue ("at 6pm", "tomorrow", "on friday") off the reminder text via the shared `_spoken_time.py` grammar; `describe_reminder` renders a speakable summary; `soonest_pending`/`next_due` resolve "the next one" for voice complete (earliest-due first, then FIFO among undated entries). English only — unlike `wake_alarms.py`, no Spanish parsing/speech branch. `config/reminders.json`.
- `calendar_events.py` — UI-free, pure parsing/shaping for voice-created **Google Calendar events**, no local persistence (Google Calendar is the only store). `parse_spoken_calendar_event` splits a trailing due-date/time cue and embedded "to my calendar" filler off the phrase (cue grammar shared with `reminders.py` via `_spoken_time.py`); unlike a reminder, a calendar event needs a date to be meaningful, so neither-date-nor-time returns `None`. `to_google_event_body` shapes the parsed dict into a Google Calendar API v3 event body (all-day vs. timed with an IANA `timeZone`); `describe_calendar_event` renders the speakable confirmation.
- `calendar_write.py` — the only module importing Google libraries: an installed-app OAuth2 write client for the Google Calendar API, scoped to `calendar.events` only (insert/update/delete — no calendar-list/ACL read). Adapted from the same pattern whatsapp-radar built for the same problem. `insert_event` is create-only (no delete/update — this issue has no cancel/edit acceptance criterion). The token is bootstrapped once via `scripts/auth_calendar_write.py`; `config/calendar_write_token.json` (gitignored, no committed sample — it's an OAuth token, not a config schema).
- `web_search.py` — Spanish voice web search (part), the UI-free core behind `POST /api/voice/search`. The Spanish pipeline stays deterministic (no LLM agent), so a search-shaped phrasing calls this: query SearXNG (`searxng_client.searxng_url()`) with `language=es`, trim to the top 8 hits × 200-char snippets (same trim as the English `web_search` function), then ONE summarising pass through the local hub (`AsyncAnthropic` at `127.0.0.1:8000`, `qwen3.5-4b-nothink`, temperature 0.2). Never raises and never answers from the model's training cutoff: SearXNG down, no usable results, and a failing/empty hub each return their own fixed Spanish sentence with their own `source` (`searxng_down` / `no_results` / `hub_error`) and warning log; every query leaves one info line (query length, result count, source, latency — never the query text). Both network edges (`_fetch_results`, `_summarise`) are single seams tests monkeypatch.
- `voice_commands.py` — the curated catalogue of every wired Voice PE command, grouped by feature and tagged per language/wake word ("Okay Nabu" English, "Hey Mycroft" Spanish; the alarm + wake-alarm groups are bilingual, which also added the card's EN/ES filter toggle), served to the PWA's "What can I say?" card by `routers/voice_commands.py`. Static prose, no I/O and no secrets (the disarm code is only ever the `<your code>` / `<tu código>` placeholder `docs/voice-pe-config/README.md` already publishes). Curated rather than derived from `custom_sentences/*.yaml` because those are hassil templates and don't cover the multi-turn grocery automation or the HA built-ins; the cost — a second place to update — is paid by step 6 of `docs/voice-commands-howto.md`'s recipe.
- `presence_client.py` — read-only iCloud Find My client: the presence *read* source (diagnostic locate + the staleness corroborator behind auto arm/disarm), while iOS Shortcuts webhooks own the automation write path; `load_presence_configs()` reads one or two Apple Accounts (`ICLOUD_EMAIL[_2]`) and `fetch_presence()` normalizes each account's devices, so two phones on separate Apple IDs merge into one snapshot; `begin_trust_renewal()` / `complete_trust_renewal()` renew Apple's ~30-day browser trust on one live session and swap it into the cached-session map.
- `device_address.py` — the "pin a device by MAC instead of IP" resolver ([network.md](network.md) "Pin a device by MAC instead of IP"). A config value that already looks like an IP or hostname is returned untouched with **no network call at all**, so no existing config has to change and the common path costs nothing; only a MAC-shaped value (`is_mac()`, anchored six-hex-pair regex so an IPv6 literal or a hex-ish hostname can never match) triggers a lookup through `network_client.resolve_ip_by_mac`. Two behaviours make it safe in front of a live device call: a short-TTL cache (`RESOLVE_TTL_S`, 120 s) so a burst of calls resolves once, and a **last-known-good fallback** — a failed inventory read returns the previously resolved address rather than raising, since a resolver that hard-fails while the router is briefly unreachable would be strictly worse than the hardcoded IP it replaces. `resolve_device_host()` (async) / `resolve_device_host_sync()` (for `scripts/ha_config_sync.py`) take a bare host; `resolve_url_host()` swaps only a URL's host, because a MAC's colons collide with the port separator and cannot sit in a URL (`HA_HOST_MAC` + `HA_URL`, used by `ha_client.py`).
- `network_client.py` — async home-network orchestrator: imports the three sub-modules below and exposes the unchanged public surface (`fetch_network_state`, `resolve_ip_by_mac`, `resolve_wireless_client_by_mac`, dataclasses) so callers don't move. `resolve_wireless_client_by_mac` backs the walk test: it reads the AP **and** the router concurrently and runs the same client merge the full snapshot uses, because the AP reports a client of the router's radio as `wired` at 100% (an uplink artefact) — an AP-only lookup would fabricate that reading into every sample.
- `network_types.py` — shared dataclasses, exceptions, and leaf helpers used across all network sub-modules.
- `network_ap.py` — NETGEAR R9000 AP: device inventory (MAC/IP/name/signal/band/SSID), AP health, `reboot_access_point`, MAC rediscovery.
- `network_router.py` — Vodafone ZXHN F6600P (ZTE): SHA256-challenge login, WAN/DHCP reads, its own radios' wireless-client read (the only source for clients attached to the router rather than the AP), binding write-back, `reboot_router`.
- `network_host.py` — host-side internet probes: ping latency + packet loss, optional speedtest, `netsh wlan`.
- `list_network.py` — CLI that prints the live network state and inventory.
- `dhcp_plan.py` — UI-free, network-free DHCP reservation planner: classifies each device into a category range from `config/dhcp_plan.json` and assigns the lowest free IP, anchoring stability on the router's existing bindings and tagging each row reserved/create/change; warns on overflow/overlap/unclassified/randomised-MAC.
- `list_dhcp_plan.py` — CLI that prints the categorised reservation plan (mirrors `list_network.py`); `--apply` pushes the create/change rows to the router behind a `yes` prompt.
- `network_display_names.py` / `network_wifi_display_names.py` / `network_hidden.py` — Network-tab label and hidden-state stores for attached devices and Wi-Fi radios; reuse `display_names.py` atomic load/save/set verbatim, parallel to the unit/plug/detector stores. `network_hidden.py` covers both attached-device (`config/network_hidden.json`) and Wi-Fi radio (`config/network_wifi_hidden.json`) hidden state in one module.
- `network_groups.py` — user-defined display groups for attached devices: normalised MAC → group name in gitignored `config/network_groups.json`, reusing the same `display_names.py` atomic helpers as the stores above, plus bulk `rename_network_group` / `delete_network_group`. Groups exist only as the set of assignments, so an empty group cannot exist and unassigned devices fall into the UI's synthetic trailing "Unclassified". Display-only and deliberately independent of `dhcp_plan.py`'s IP-range categories.
- `network_oui.py` — offline device identification: bundled trimmed OUI→vendor table, randomised-MAC detection, and a category/icon heuristic (no network call, render-time).
- `network_history.py` — per-MAC history store (SQLite, modeled on `energy_history.py`): first/last/times-seen, the last-known IP/hostname/band/SSID, the `important` flag, and the online/offline + new-device derivations. Columns added after it shipped are topped up by an idempotent `ALTER TABLE` sweep in `init_db`. Recorded on each `/api/network` read (no background sampler — the AP read is expensive and tab-gated); randomised MACs are never tracked. Kept separate from the rename/hidden stores; gitignored `webapp/network_history.sqlite3`. The same file also holds an `internet_samples` series (latency / loss / speed-test results, one throttled sample per `/api/network` read, 30-day retention) read by `GET /api/network/internet-history` for the internet tile's sparklines. Connection mechanics come from `_sqlite.py`.
- `network_survey.py` — Wi-Fi walk-test sample store (SQLite, sibling of `network_history.py`): one append-only row per user-initiated coverage sample — room label, client MAC, the AP/router-measured signal/link-rate/band/SSID and which box reported it, plus the browser-measured RTT/jitter/loss/throughput. A MAC on neither radio is stored as `source='not_found'` with a null signal so "no coverage here" stays a distinguishable state rather than a blank. Deliberate user writes only (no poll, unlike the history store); 365-day retention pruned on write; gitignored `webapp/network_survey.sqlite3`. Connection mechanics come from `_sqlite.py`.
- `dhcp_overrides.py` — per-MAC category overrides chosen in the Network tab UI; persisted to gitignored `config/dhcp_overrides.json` and merged over `config/dhcp_plan.json` by the planner so a UI choice wins without editing the committed config.
- `camera_client.py` — async, UI-free camera core: ONVIF for discovery/profiles/PTZ (`ContinuousMove` / `Stop` / `AbsoluteMove`, preset management), RTSP + ffmpeg for snapshot / MJPEG stream / clip recording. Returns a flattened `CameraInfo` per declared camera; capabilities (`ptz_presets`, `ptz_absolute`, `ptz_relative`) gate the UI controls. Cameras declared in gitignored `config/cameras.json`.
- `camera_ffmpeg.py` — ffmpeg subprocess wrapper used by `camera_client.py` for RTSP→JPEG snapshot, RTSP→MJPEG stream transcoding, and server-side mp4 recording. Every ffmpeg call is dispatched to a lazily-started background thread running its own persistent `ProactorEventLoop` — Windows only supports `asyncio` subprocess transports on the proactor loop, but the webapp's own uvicorn loop is the selector loop (the fix for the accept-loop wedge), so ffmpeg calls can't run directly on the server's own loop.
- `camera_display_names.py` — custom label store for camera IDs; parallel to `display_names.py`; persisted to gitignored `config/camera_display_names.json`.
- `camera_presets.py` — software PTZ preset store for cameras that lack native ONVIF preset support; persisted to gitignored `config/camera_presets.json` (absolute pan/tilt/zoom coordinates).
- `camera_preset_names.py` — custom label store for camera preset tokens, keyed by `"camera_id::token"`; persisted to gitignored `config/camera_preset_names.json` via `display_names.py`'s atomic load/save, only the composite key and on-disk path differ.

## `app/webapp/` — the FastAPI + PWA product

- `server.py` — `create_app()`, middleware, caching static mount, routers, background-task lifespan. Lifespan startup starts the write-side automation-loop tasks below only when the launcher opted in (`HOME_AUTOMATION_ENGINES=1`; otherwise it logs `automation engines off` and starts none) and it then wins `src.automation_owner.AutomationOwnership` — a second instance still mounts every router and serves read-only.
- `middleware.py` — bearer-token / loopback auth gate, (response compression is the vendored `src/compression.py`).
- `observability.py` — the pure-ASGI slow-request middleware, just inside the compression layer: a line in `webapp/slow-requests.log` for each GET to `/` or a phone-polled API read over its 0.25 s budget, and for any request over 3 s; streams (SSE, MJPEG) pass through unbuffered and are never logged.
- `manager.py` — adopt-or-spawn / restart / stop for the uvicorn webapp (used by the tray).
- `sampler.py` — background energy sampler owned by the webapp lifecycle.
- `speedtest_schedule.py` — opt-in nightly speed-test loop owned by the webapp lifecycle: started only by the automation owner, a minute tick that runs the host-side test once from 03:00 (catch-up until 06:00, bounded retries) when `src/network/speedtest_prefs.py` says so, and stores the result in `network_history`'s `internet_samples`. The store is its memory, so a restart cannot repeat a night. Off by default.
- `read_snapshot.py` — `ReadSnapshot`, the in-memory snapshot of a slow read: a demand-gated background refresh, a staleness bound past which a read fetches inline, the snapshot's age in every answer, and sequence-numbered write patches/dirty marks a fetch already in flight can't overwrite. Wired: `/api/units`, `/api/security`, `/api/hyperv`, `/api/energy`, `/api/tuya`, `/api/ups`, `/api/weather` (off the request path so Open-Meteo latency never lands in a request; the location PUT invalidates it), each declared in its router as `<NAME>_SNAPSHOT` with its own tick and staleness bound. Router writes patch in their read-back; writers outside a router (the HVAC automation loop, alarm schedules, auto-bypass, the actions registry) call `read_snapshot.invalidate(<name>)`, and the lifespan starts every registered tick. `warm()` fetches once at boot (the owner warms energy, so the Modbus rediscovery isn't paid inside a request). `stale_after_s` makes a snapshot serve-stale (`/api/energy`): once it holds a value a read never fetches inline, answers with the last reading and one shared background task refreshes it; past `stale_after_s` the `snapshot` block carries `stale: true` plus the last refresh's `error`, and the PWA labels the tile instead of plotting it as live. `demand_window_s=0` turns the tick off (`/api/network` and `/api/circuits`, `/api/lights` and `/api/ha`): serve-stale snapshots over home hardware this app must never poll on its own (the AP's ~8 s SOAP read, the router, the CT-clamp meters, the Elgato mDNS sweep, the Home Assistant websocket read), so a refresh only ever follows a read and concurrent readers share one device read. The LAN snapshot records device/internet history once per real read, not per answer; its overlays (names, groups, hidden, `important`) merge per request. `?speedtest=1` stays a live read.
- `automation.py` — background HVAC automation evaluator (dynamic setpoint rules + schedules) owned by the webapp lifecycle.
- `security_automation.py` — background weekly alarm-schedule evaluator owned by the webapp lifecycle.
- `blind_schedules.py` — background daily blind-schedule evaluator: the HVAC engine's narrow catch-up window (`_schedule_store.daily_due`, lifted out of `automation.py`) and once-a-day gate, a presence check at fire time, and `src.devices.blind_automation.move_blinds` for the move. `BLIND_SCHEDULES_ENABLED` switches it off. Also `follow_alarm()`, which `presence_automation.tick()` awaits after a confirmed, recorded arm/disarm; it never raises. Both paths hand a failed blind to a background retry task that records the settled move with its attempt count and, on final failure, sends one Telegram message through `notify_config.build_alarm_notifier`; `settle_manual_move()` gives the Blinds card's manual taps the same retry and message, without the record.
- `wake_alarm_automation.py` — background wake-alarm + timer evaluator owned by the webapp lifecycle: fires due alarms (marks "ringing", best-effort Telegram notify, rearms weekly / auto-disables one-shot) and expires due timers.
- `presence_automation.py` — background presence → alarm automation consumer (evaluates webhook-backed presence state and fires arm/disarm) owned by the webapp lifecycle.
- `security_override_automation.py` — auto-bypasses a detector after repeated same-session alarms per its configured `security_override.py` rule; reuses the event-log-diff architecture (diffs `fetch_events()` against a persisted cursor rather than the live intrusion flags) and rides `presence_automation.py`'s single RISCO read instead of a second poller. Restores every auto-bypassed zone on the next arm event; logs via `src.telemetry.record_event` (`auto_bypass` / `auto_unbypass`), surfaced by `GET /api/activity`.
- `alarm_notify.py` — single `record_alarm_action()` entry point used by the schedule, presence, and manual arm/disarm paths: always appends to the `logs/alarm.jsonl` activity log, and sends a Telegram alert only for automatic sources whose toggle is on (manual never notifies; errors de-dupe to once/day). Also `record_security_event()` / `check_security_transitions()` for edge-triggered intrusion + panel-AC alerts off the presence loop's RISCO read.
- `power_monitor.py` — background task (webapp lifespan) that polls the UPS every `POWER_MONITOR_POLL_INTERVAL_S` in a worker thread, fires `power_notify.record_power_event()` on each mains↔battery transition (the server-side watcher behind the power-loss Telegram alerts), and enforces the low-battery safety shutdown: edge-triggers `power_notify.record_low_battery_shutdown()` once per outage when on-battery runtime drops to or below `pc_fleet_prefs.PcFleetPrefs.threshold_minutes` (read fresh each tick, default 15 min, falling back to a hardcoded 15-min constant if prefs can't be loaded — fires even on the monitor's first observation, unlike the mains-transition alerts), cancelling via `record_low_battery_shutdown_cancelled()` if mains power returns first.
- `power_notify.py` — `record_power_event()`: appends UPS power transitions to `logs/power.jsonl` and sends a Telegram alert per the `power_lost`/`power_restored` toggle. `record_low_battery_shutdown()` / `record_low_battery_shutdown_cancelled()`: the safety-net pair — always logs, and when `pc_fleet_prefs.PcFleetPrefs.enabled` is on, sends a distinct Telegram alert, sweeps included/up satellites via the hub's loopback API, and calls `src.host_shutdown` to schedule/cancel the tower's own OS shutdown (which always goes last) or, for `tower_action = hibernate`, runs an in-process grace timer that calls `initiate_hibernate` (`shutdown /h`) and is cancelled when mains returns.

- `alarm_scene_automation.py` — alarm-triggered scene capture + AI verdict orchestrator: the glue between the RISCO alarm and `src.security.alarm_scene`. Does not poll RISCO itself — rides the presence loop's single `SecurityState` read each tick, does the cheap due-check inline, and fires the expensive event-log-read + capture + vision-call work as a detached task. A `docker compose` command that exits 0 without restoring `/healthz` is recorded as a failure, never a recovery. Registered inside the lifespan's automation-ownership branch so only one process supervises the container.

Read-only, so every instance runs it, engines on or off; handles and working-set size come from the Windows process APIs and print `?` elsewhere.
